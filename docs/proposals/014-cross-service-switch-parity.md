# Proposal 014：跨服务开关校验 —— 结论是不做

## 0. 结论

issue #23 §2 把「跨服务配置」列为 ❌，并附了唯一带真实事故背书的动机（某开关只配了一侧，P95 拖到约 12 秒、持续约 6 天）。本提案起草了两版引擎侧方案，**两版的前提都被目标仓的真实代码推翻**。第三次重推的结论是：

> **引擎侧不做这个机制。** 替代动作有两条，都在目标仓：①一个覆盖「声明 → 消费端」的契约测试（§4.1）；②给 env fallback 加**运行时可观测 + 跨服务分歧告警**（§4.2）——这条才真正降低那次事故的复发风险。
>
> **「引擎侧不做」不等于风险已消除。** §3 记录的取值分歧仍然活着且无人防护，所以在 §4.2 落地前，issue #23 那一行必须继续是 ❌，只补处置状态、不改成结论项（§4.3）。

写下这份文档的价值不在方案，在于**两次前提失效的记录 + 一处我自己搞反的风险判断（§3）**——避免第三个人从 issue #23 那句「20 个直接比较式开关」出发再设计一遍，也避免有人引用 v2 那句错误的「单一真相源，两侧不可能不一致」。

---

## 1. v1 前提失效：那 20 个开关的采集口径已经过期

v1 设计：adapter 提取 `process.env.X === "true"` 读取点，人在 config 里声明 `sides: [A, B]`，引擎 diff。

在 目标仓A `origin/main`（9 个已声明组件）实测：

| v1 假设 | 实测 |
|---|---|
| 开关是 `process.env.X === "true"` | 该写法正在被淘汰。`packages/flags/src/registry.ts` 明写它是「迁移前的口径」，并立规矩：**只有真正接线的 flag 能进注册表，否则就是 split-brain** |
| 需要人新写配对契约声明 | 部分成立，但**理由不是「第二真相源」**（见下方更正）。registry 声明的是**取值语义与 exposure**（key、来源、默认值、是否暴露给 sandbox/browser），**不声明哪些组件必须消费某个 flag**——那份知识今天确实缺失。v1 真正致命的是它既检测不到部署值，扫描口径又已过期 |
| 20 个候选开关 | 注册表 **11 个**条目；非测试代码里被 `getFlag` 读到 **10 个**，其中 **7 个跨 ≥2 组件**——跨组件普遍到它本身不是异常信号，v1 那条「readers ≥ 2 即为候选」会一次性列出大半个注册表 |

**issue #23 里那个「20」采集于 flags 迁移之前。** 方案的前提数字必须在动手前回目标仓复核，否则会精确地解决一个已经不存在的问题。

**一处需要更正的措辞（本文初稿写错过，记下来避免被引用）**：初稿称「registry 就是那份配对声明，再写一份是造第二真相源」。这不准确——registry 是**取值与 exposure 目录**，不是消费方契约。它既没有声明 exposed key 的消费者清单，也没有门禁阻止已登记的 `envKey` 被业务代码在 flags 包外直接读取。所以否掉 v1 的理由应当落在「读不到部署值 + 扫描口径已失效」，不能落在一个不成立的「重复声明」判断上。

## 2. v2 前提失效：那条「三跳送达链」的中间一跳是自动的

v2 改为校验 `exposeToSandbox` 的送达链：registry 声明 → 两份平行实现的 `/api/internal/config/[key]` 路由都要供给 → agent-worker 的 poller 消费。这一版同样不成立：

| v2 假设 | 实测（`origin/main`） |
|---|---|
| 两份 route 要**分别为每个 flag 配线** | **自动派生**：两份 route 都是 `const READERS = getSandboxFlagReaders();`。新增一个 `exposeToSandbox` key 会自动流到两侧，没有人工步骤，`packages/flags` 还有派生行为的测试 |
| 有一批 flag 走这条链 | **只有 1 个**：`exposeToSandbox: true` 全仓仅 `registry.ts:255` 一处 |
| 断裂时「没有任何地方报错」 | 不准确。poller 对缺 URL/token、非 2xx、网络与解析失败**都 `console.warn`**。准确的说法是**用户效果静默**（fail-closed 成 `false` 且负缓存），日志有痕迹——这是**观测/告警缺口**，未必是结构缺口 |

真正需要人配套的只剩一处：**声明 → 消费端**（poller 硬编码 `V2_DELIVERY_ENABLED_KEY = "v2_delivery_enabled"`）。

**为一个人口为 1、中间跳自动派生、末端硬编码一个常量的场景，造一套引擎机制（新 adapter 字段 + 新 config 段 + 新 check 模块 + CLI 接线 + 目标仓 adapter 改动）——收益与成本明显不成比例。**

**两跳要分开说，不能一句「自证通过」打包否掉**（初稿混为一谈了）：

- **声明 → 两份 route** 这一跳确实是**自比较**：READERS 从同一份 registry 派生，再造事实去和 registry 比对，等于让它自己证明自己。
- **声明 → 消费端**这一跳**不是**自比较——poller 的硬编码常量并非从 registry 派生，两者确实可能脱节，这是真实的契约。否掉它的理由不是「自证」，而是：**population = 1**，且 §4.1 那个目标仓测试用近乎零的成本就能覆盖同一个失效。引擎机制在这里没有增量。

## 3. 一处我自己搞错、且方向相反的判断（必须记下来）

v2 曾断言「9/11 个 flag 从同一个 FDC dataId 取值，单一真相源，两侧不可能不一致」，据此把「两侧配套」的风险面缩到只剩 2 个 `envKey`-only flag。**这是错的。**

`packages/flags/src/resolve.ts` 的解析链是 `FDC → env fallback → declared default`，而 **env fallback 是每个进程各读各的 `process.env`**。所以当 FDC 可达但字段缺失、文档被清空、值无法解析，或 FDC 降级时，各组件会各自落回**自己那份 env**。不同组件部署了不同 env 值时，那 8 个「FDC + env fallback」的 flag **仍可重现 v1 描述的分歧**。

也就是说 v2 不但发明了一个基本自动的问题，还把一个**真实存在的风险面从范围里删掉了**。这条修正比方案本身重要。

## 4. 替代动作

### 4.1 目标仓：一个契约测试（应该做，成本近乎为零）

在 目标仓A 加一个测试，枚举 registry 里全部 `exposeToSandbox: true` 的 key，断言：

- 通用 route bridge 存在（`getSandboxFlagReaders()` 能把它们解析出来）；
- **每个 key 都有明确的消费端**——这是唯一真正手工配套的一跳，也是 v2 唯一说对的地方。

摘掉 poller 的 key 常量、或新增一个自动进入两份 route 却没有 consumer 的 exposed flag，该测试都必须变红。

**这一步独立成立，不依赖 codeontic 任何改动。**

### 4.2 目标仓：给 env fallback 加运行时可观测（这条才真正降低 §3 的风险）

§3 那条——**带 env fallback 且跨组件读取的 flag，在 FDC 降级/字段缺失时各读各的 env**——是真实且**当前无人防护**的风险。它取决于各环境实际部署的 env 值，属于运行时事实，**静态分析读不到**（issue #23 §4 硬规则：没有外部真相源就不做）。

**但「静态查不到」不等于「只能记一笔」。** 只写进文档不会检测、也不会缩短下一次分歧的存活时间——那次事故正是持续了约 6 天没人发现。真相源不必是静态的：**进程自己就知道它落回了 env**。

所以替代动作是运行时可观测，而不是静态检查：

- **所有相关服务都要上报当前生效值，不能只在 fallback 时上报。** 这一点是本节的关键，也是初稿写错过的地方：若只在 fallback 时发信号，那么「服务 A 正常从 FDC 读到 `true`、服务 B 局部降级回落到 env=`false`」这种**非对称**分歧**永远不会告警**——聚合器只收到 B 的信号，手上没有 A 的当前值可比。而这恰恰是最可能真实发生的形态（分歧本来就常常是单侧降级造成的）。所以上报要覆盖**每一次解析结果**（或按周期刷新当前值），而不是只覆盖异常分支。
- 每条信号带：flag key、服务/进程标识、环境、**来源**（`fdc` / `env` / `default` / `last-known-good`）、fallback 原因（字段缺失 / 文档为空 / 值不可解析 / FDC 降级 / 冷启动），以及**安全表示**的生效值。来源字段是必需的——同一个 `false`，来自 FDC 和来自 env fallback 是两件事。
- **按「同环境 + 同 flag + 不同服务的生效值不一致」聚合告警。** 直接对应事故形态，完全不需要静态分析。
- 当前 `resolve.ts` 只有 FDC 降级那条路径告警，其余 fallback 可以无声发生——这是缺口所在。
- 验收用例必须包含**非对称场景**：一侧正常读 FDC、另一侧 fallback，且两者取值不同 → 必须告警。只测「两侧都 fallback」会让上面那个漏报活下来。另需覆盖四条 fallback 路径：字段缺失、空文档、不可解析、FDC 降级。

若将来部署配置本身进了仓库且可结构化解析，静态侧可以重开——但那不是等待这条的理由。

### 4.3 issue #23 §2 那一行怎么改

**在 §4.2 的运行时保护落地之前，这一行应当继续是 ❌（已知未解决），不要改成「已处置」。**

理由：引擎侧撤回只说明「这个机制不该由 codeontic 做」，不说明风险消失了。§4.1 的契约测试只覆盖当前唯一那条 `exposeToSandbox` 链路，与 §3 的取值分歧**完全正交**——它一条都防不住。把一个仍会重演六天事故的维度标成结论项，制造的正是本仓反复在治的「信号谎报自己状态」。

建议的行文是给 ❌ **补上处置状态**而不是取消它：**「❌ 未解决。引擎侧不做（Proposal 014，含两次前提失效记录）；目标仓侧待办：①声明→消费契约测试 ②env fallback 运行时可观测 + 跨服务分歧告警。②落地后方可复评此行。」**

## 5. 这次调研本身的方法论教训

1. **前提数字必须回目标仓复核。** 两版方案都栽在同一件事上：从 issue 里一个历史数字出发做设计，而那个数字的采集口径已经变了。
2. **「读注释和文件名」不等于「读代码」。** v2 把两份 route 描述成手工配线，是因为看到两个平行文件就下了结论；实际只要多看一行 `const READERS = getSandboxFlagReaders();` 就会发现是自动派生。
3. **「静默」这个词要分清是哪一种。** poller 其实 `console.warn` 了。把「用户效果静默」说成「没有任何地方报错」，会把一个观测/告警问题误判成结构问题，进而推出一个错误的解法。
4. **人口规模是设计的一等输入。** population = 1 时，几乎任何通用机制都是过度设计；这个数应该在画架构图之前就查。
