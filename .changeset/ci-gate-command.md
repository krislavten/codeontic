新增 `codeontic gate` —— CI 门禁入口，把接入仓过去手写在 workflow 里的那套逻辑收进引擎：跑确定性检查、（可选）对基线打分、只为**本次改动引入的** error 判红、渲染裁决、返回退出码。

`--base <ref>` 是关键能力：把基线 ref **检出到临时 worktree**，在那里跑**同一个** check，"是不是本次引入"就是两侧 findings 的集合差。

这里先试过"不检出基线、用 git plumbing 给它打分"，代价是每接一个检查都要单独发明一套归因法，而每套都差一点：锚点存在性在 base 侧用 `git ls-tree` 精确匹配、HEAD 侧用 `stat`（会规范化 `./x` 这类写法），于是真删了文件反而两侧同文案、判成"基线本来就坏"；INV-1 是 AST 扫描，没有文件就没法跑，先被整个排除出门禁（接入仓把 CI 从 `check` 换成 `gate` 就静默失去这层拦截），后来改用"文件被碰过没"来归因，结果给一个含陈年违规的文件加一行 import 就判成本次引入。检出之后这些问题一次性消失，也不再需要 per-check 归因逻辑。成本实测不构成理由：4.4k 文件的仓库上检出约 0.5s、全量 check 约 0.5s。worktree 的清理放在 `finally`，git 与文件系统两侧都清。

`--format github` 把裁决写进 `$GITHUB_STEP_SUMMARY`（归因文案由引擎按真实 `Violation` 生成，消费方不必再 grep 输出反解成因）。

为什么做成命令而不是配方：第一个把这一档晋升为阻塞的接入仓，把它写成了约 70 行 workflow shell，而那次晋升发现的每个 bug 都在那些行里，且没有一个与目标仓库有关——`bash -e` 下裸重定向让比对还没跑就终止；空错误集减任何集合都是空，于是管线故障被判成"基线本来就坏"而**门禁静默变绿**；比对键是从人读输出里正则截出来的、只截到节点 id，同节点上新坏的第二个锚点因此被旧账吞掉。这三类在引擎里结构性不可能：比对跑在带类型的 `Violation` 上，"没有错误"和"跑不起来"是不同的值而非同一个空字符串，退出码是返回值。
